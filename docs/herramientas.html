CÓMO NACE EL GOAL

de una idea difusa a un objetivo que se puede fallar
◢ POR QUÉ EXISTE

"Quiero mejorar X" no dirige nada. El módulo /goal convierte esa idea difusa en un objetivo investigado y medible ANTES de planificar: se investiga una vez, y todo el ciclo hereda ese norte.

EL DISCO
Se escribe el goal: un resultado que se puede fallar ("el visor abre un archivo .LAS y pinta 3 curvas en menos de 2s") con su "sabremos que funcionó cuando…". Si el objetivo no tiene número posible, se congela una rúbrica: criterios fijos ANTES de construir, para que nadie mueva la portería después
adw/goal.md

TÚ
Revisas y apruebas el goal. Es tu control de calidad: si el objetivo está mal, todo lo que se construya encima estará bien hecho… para el objetivo equivocado
tu visto bueno, en la conversación

◢ LA CLAVE

Dos researchers que no se ven + un verifier de fuentes + la conciliación en manos del orchestrator, que tiene el contexto completo = un objetivo en el que se puede confiar. Se paga una vez por proyecto, y evita el error más caro de todos: construir rápido hacia el lugar equivocado.

EL CÓDIGO DE CADA SISTEMA

todo vive en una carpeta .claude/ que se copia al proyecto

No hay programas externos ni servidores: cada método es una carpeta .claude/ con cuatro tipos de pieza — skills (protocolos que sigues con /comandos), agentes (los roles del equipo), hooks (vigilantes automáticos) y scripts (mecánica pura en bash/python). El 03 nació del 02: comparten casi todo.
